        Framework and YANG Data Model for the NMA A2U Interface
                  draft-zhao-nmop-nma-a2u-interface-00

Abstract

   This document describes a framework and a YANG data model for the
   Agent-to-User (A2U) interface of a Network Management Agent (NMA).
   The A2U interface is a user-facing interface through which a non-
   agent upper-layer system or user, such as an operator's OSS/BSS,
   orchestrator, management portal, human-facing application, automation
   system, etc., interacts with an NMA.

   The A2U interface supports NMA capability discovery, unified intent
   submission, task lifecycle management, execution plan exposure,
   human-in-the-loop confirmation, event notification, and consistent
   error reporting.

   The YANG data model defined in this document describes protocol-
   binding-independent information objects and message structures used
   by the A2U interface.  This document does not mandate a specific
   protocol binding.  An HTTP-based realization using JSON and Server-
   Sent Events (SSE) is provided as a non-normative example.

1.  Introduction

   Telecommunication networks are becoming increasingly complex in
   scale, technology composition, service diversity, and operational
   requirements.  Traditional manual operation and fixed API-based
   management are often insufficient to support highly automated and
   adaptive network operations.

   A Network Management Agent (NMA) is an autonomous or semi-autonomous
   management entity with awareness, analysis, decision-making, and
   execution capabilities.  It can interpret user goals, plan management
   actions, invoke tools and interfaces, monitor execution, and report
   results.

   To allow non-agent upper-layer systems and users to consume NMA
   capabilities in a uniform way, this document defines the Agent-to-
   User (A2U) interface.

   The A2U interface supports:

   *  NMA capability discovery;

   *  natural-language or structured intent submission;

   *  task lifecycle monitoring;

   *  execution plan exposure;




Zhao                     Expires 1 January 2027                 [Page 3]

Internet-Draft              NMA A2U Interface                  June 2026


   *  human-in-the-loop confirmation;

   *  event notification;

   *  consistent error reporting.

   A2U is intended for client/server-style interaction between a non-
   agent upper-layer system or user and an NMA.  It is not intended for
   communication between an upper-layer NMA and a lower-layer NMA.  NMA-
   to-NMA or Agent-to-Agent communication is outside the scope of A2U
   and is expected to use A2A or other Agent-to-Agent interfaces.

   The A2U YANG data model is protocol-binding independent.  It
   describes the information exchanged across the A2U interface, but it
   does not require that A2U objects be exposed as configuration
   datastore nodes.

   An HTTP-based realization is provided in Appendix A.  In such a
   realization, A2U may use /nma/a2u/* resources and be logically
   separated from the traditional RESTCONF configuration plane using
   /restconf/*, while sharing the same TLS and authentication
   infrastructure.

3.  Terminology

   A2U Interface
      The Agent-to-User interface through which a non-agent upper-layer
      system or user consumes NMA capabilities.
   Network Management Agent (NMA)
      A network management entity defined in [I-D.zhao-nmop-network-
      management-agent] that interprets management goals, plans tasks,
      invokes tools or interfaces, monitors execution, and reports
      results.
   A2U Client
      A non-agent upper-layer system or user-facing application that
      uses the A2U interface.  Examples include an operator's OSS/BSS
      systems, orchestrators, management portals, automation systems,
      and human-facing applications.  An upper-layer NMA is not an A2U
      Client in this document.

   Intent
      A goal description submitted to the NMA.  It can be expressed
      using natural language or structured data.
   Task
      A management operation unit instantiated by the NMA for an
      accepted intent.
   Plan
      A sequence of steps generated by the NMA to execute a task.
   Confirmation
      A pending decision object generated when a task requires explicit
      approval, rejection, modification, or escalation.
   Event
      A task-related notification generated by the NMA.
   Agent Card
      The capability discovery object returned by the NMA.
   A2A Interface
      An Agent-to-Agent interface used for interaction between agents or
      NMAs.  A2A is outside the scope of this document.
   A2C Interface
      The Agent-to-Controller interface between the NMA and controller
      functions.
   A2N Interface
      The Agent-to-Network interface between the NMA and network
      resources, or the corresponding extended southbound capability in
      an integrated deployment.

5.  A2U Interface Positioning

   A2U is used when a non-agent upper-layer system or user invokes NMA
   capabilities.

   In the A2U model:

   *  the A2U Client is a non-agent system or user;

   *  the NMA exposes capabilities upward;

   *  the client submits intents or requests;

   *  the NMA manages parsing, planning, execution, confirmation, event
      reporting, and result generation;

   *  the client observes, confirms, or aborts the task when required.

   A2U is not used when an upper-layer NMA communicates with a lower-
   layer NMA.  Such communication is Agent-to-Agent communication and
   should use A2A or other Agent-to-Agent interfaces, because both sides
   may need peer-agent semantics such as capability negotiation, task
   delegation, collaboration, commitment, trust establishment, and
   result aggregation.

   The A2U interface is distinct from:

   *  A2A, used between agents or NMAs;

   *  A2C, used between the NMA and controller functions;

   *  A2N, used between the NMA and network resources.

   The A2U Service Function provides capability discovery, intent
   submission, task monitoring, plan exposure, confirmation handling,
   event notification, and result reporting.

   The A2U data model defined in this document focuses only on
   information exchanged across A2U.  It does not define the internal
   NMA architecture, internal A2C mechanisms, or extended southbound
   mechanisms.

   In the independent deployment mode, the NMA may be deployed beside
   the Network Controller.  In that case, the NMA exposes A2U upward,
   interacts with the controller through A2C, and interacts with network
   resources through A2N.

7.  A2U Design Principles

7.1.  Logical Separation

   In an HTTP-based realization, A2U may share the controller's HTTPS
   port, TLS session, and authentication system, but it is logically
   separated from the configuration plane.

   For example:

   *  /restconf/* may be used for RESTCONF configuration and operational
      datastore access;

   *  /nma/a2u/* may be used for A2U interaction.

7.2.  Protocol-Binding Independence

   The A2U YANG model defines information objects and message
   structures.  It does not mandate HTTP, RESTCONF, NETCONF, gRPC, or
   any other protocol binding.

7.3.  Unified Intent Entry

   Natural-language and structured input share the same intent
   submission entry and the same task lifecycle.  The mode field
   distinguishes the input type.

7.4.  Unified Task Lifecycle

   After an intent is accepted, the NMA creates or associates a task.
   The task lifecycle includes:




Zhao                     Expires 1 January 2027                 [Page 8]

Internet-Draft              NMA A2U Interface                  June 2026


   PENDING -> ANALYZING -> PLANNING -> AWAITING_CONFIRMATION
           -> EXECUTING -> COMPLETED / FAILED / ABORTED

                       Figure 2: Lifecycle of a task

   Clarification may be requested when input is incomplete or ambiguous.

7.5.  Human-in-the-Loop Confirmation

   When a task exceeds an autonomy level, violates a policy, affects
   critical resources, or requires human review, the NMA creates a
   confirmation object and suspends execution until the confirmation is
   resolved.

7.6.  Event Streaming and Polling

   The NMA reports task progress through typed events.  Events may be
   delivered by streaming, polling, or other binding-specific
   mechanisms.

8.  A2U Information Model

   The A2U information model contains five core components.

8.1.  Agent Capabilities

   The agent-capabilities object, also called the Agent Card, describes
   the NMA and its exposed skills.  It includes:

   *  agent identifier;

   *  version;

   *  skill list;

   *  input schema for each skill;

   *  confirmation requirement;

   *  maximum autonomy level;

   *  optional tags for skill classification and discovery;

   *  endpoint list;

   *  global policies.





Zhao                     Expires 1 January 2027                 [Page 9]

Internet-Draft              NMA A2U Interface                  June 2026


8.2.  Intent

   The intent object represents a user or system goal.  It includes:

   *  intent identifier;

   *  input mode;

   *  submitter information;

   *  timestamp;

   *  state;

   *  associated task identifier;

   *  natural-language or structured input;

   *  estimated completion time.

   Natural-language input may include the original user text, parsed
   result, and parser type.  Structured input includes operation type,
   target resource, constraints, and priority.

   The intent-type identifies the high-level operation category.  It is
   not intended to encode all domain-specific subtypes.  Domain-specific
   details, such as service assurance objectives, fault symptoms,
   recovery constraints, or optimization policies, are carried in the
   constraints field.

   The base operation categories include creation, deletion,
   modification, query, reporting, diagnosis, remediation, optimization,
   and assurance.  For example, service assurance is represented by
   ASSURE; fault analysis is represented by DIAGNOSE; corrective fault
   handling or service recovery is represented by REMEDIATE.

8.3.  Task

   The task object represents the lifecycle of an accepted intent.  It
   includes:

   *  task identifier;

   *  parent intent identifier;

   *  state;

   *  creation and update timestamps;



Zhao                     Expires 1 January 2027                [Page 10]

Internet-Draft              NMA A2U Interface                  June 2026


   *  plan;

   *  result;

   *  audit log.

   The plan is a list of steps.  The audit log records important task
   actions.

8.4.  Confirmation

   The confirmation object represents a pending or resolved decision
   point.  It includes:

   *  confirmation identifier;

   *  task identifier;

   *  confirmation type;

   *  priority;

   *  timeout;

   *  context;

   *  allowed actions;

   *  status;

   *  resolution details.

   The resolution container records the final decision made for a
   confirmation, including the selected action, any modified parameters,
   the resolver, and the resolution time.

8.5.  Event

   The event object represents task-related notifications.  It includes:

   *  event identifier;

   *  event type;

   *  task identifier;

   *  timestamp;




Zhao                     Expires 1 January 2027                [Page 11]

Internet-Draft              NMA A2U Interface                  June 2026


   *  recipient;

   *  typed payload.

   The event payload is modeled as a choice so that different event
   types carry different payload structures.

9.  YANG Data Model

9.1.  Model Design

   This document defines a single YANG module, ietf-nma-a2u.

   The module uses the YANG data structure extension defined in
   [RFC8791].  The sx:structure statements describe abstract information
   objects and message bodies exchanged across A2U.  They are not
   configuration datastore nodes.

   Only the top-level structures use the nma-a2u- prefix in their names,
   in order to distinguish A2U structures from other future NMA
   interface structures.  Fields inside the structures keep short names
   for readability.

   The reusable groupings use the -object suffix, such as intent-object
   and task-object, to distinguish reusable object templates from
   instantiated containers and top-level structures.

10.  Security Considerations

   The A2U interface can expose sensitive operational information,
   including intents, tasks, plans, affected resources, confirmation
   context, event streams, and audit information.

   Implementations are expected to provide authentication,
   authorization, confidentiality protection, integrity protection,
   replay protection, audit logging, and policy enforcement.

   Natural-language inputs and AI-assisted interpretation may introduce
   risks such as ambiguous instructions, malicious input, prompt
   injection, or incorrect interpretation.  Implementations should
   validate interpreted results before execution and should use
   confirmation or policy checks for risky operations.

   Confirmation resolution operations can affect network behavior and
   therefore require authorization and audit logging.

   Event streams may contain sensitive operational information.
   Implementations should ensure that event subscribers are authorized
   to receive the corresponding events.

   Future versions of this document are expected to expand this section.

Appendix A.  Example HTTP-Based Binding

   This appendix describes one possible HTTP-based realization of the
   A2U interface.  It is provided as an example protocol binding and is
   not intended to mandate HTTP as the only implementation mechanism.

A.1.  General Rules

   In this example binding:

   *  A2U resources use the /nma/a2u/* URI space;

   *  RESTCONF resources may use the /restconf/* URI space;

   *  JSON is used for request and response bodies;



Zhao                     Expires 1 January 2027                [Page 44]

Internet-Draft              NMA A2U Interface                  June 2026


   *  Server-Sent Events (SSE) may be used for event streaming;

   *  TLS, authentication, authorization, and audit logging are required
      by the implementation.

A.2.  Capability Discovery

   GET /nma/a2u/agent-capabilities

   Response body: nma-a2u-agent-capabilities.

A.3.  Intent Submission

   POST /nma/a2u/intent

   Request body: nma-a2u-submit-intent-request.

   Response body: nma-a2u-submit-intent-response.

   Possible responses include:

   *  200 OK for synchronous result;

   *  202 Accepted for asynchronous task creation;

   *  200 OK with text/event-stream for streaming scenarios.

A.4.  Task Retrieval

   GET /nma/a2u/tasks/{task-id}

   Response body: nma-a2u-task.

A.5.  Task Listing

   GET /nma/a2u/tasks

   Response body: nma-a2u-task-list-response.

   Optional query parameters include state, submitter-id, limit, and
   offset.

A.6.  Event Subscription

   GET /nma/a2u/tasks/{task-id}/events

   Response body: SSE stream carrying nma-a2u-event objects.




Zhao                     Expires 1 January 2027                [Page 45]

Internet-Draft              NMA A2U Interface                  June 2026


   Example SSE frame:

   id: <event-id>
   event: <event-type>
   data: <JSON-encoded nma-a2u-event>

A.7.  Confirmation Resolution

   POST /nma/a2u/confirm

   Request body: nma-a2u-confirmation-resolution-request.

   Response body: nma-a2u-confirmation-resolution-response.

A.8.  Task Abort

   POST /nma/a2u/tasks/{task-id}/abort

   Request body: nma-a2u-abort-task-request.

   Response body: nma-a2u-abort-task-response.
